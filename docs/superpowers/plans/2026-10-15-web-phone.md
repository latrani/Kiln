# Web-native Kiln, part 4: phones (layout and PWA) — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The web build works on a phone, held in one hand, and installs to the Home Screen:
- **Layout:** the same five areas, rearranged for a narrow screen. The sidebar becomes a drawer behind a `≡` chip.
- **Touch:** everything that's only a key today (Esc, log mode's letters, shift-click) gets something to tap.
- **The soft keyboard:** the input stays above it, and it only comes up when you tap to type.
- **PWA:** a manifest, icons and a small service worker, so Kiln installs on iOS and Android and can notify there.

**Architecture:** All page-side, plus build and relay plumbing. One `narrow` signal (a media query, `useNarrow()`) picks the layout; one `touch` signal (`(pointer: coarse)`) adds the tap targets and stops auto-focus. They're separate because an iPad is touch but wide, and a narrow desktop window is narrow but has a keyboard. Go doesn't change, except `kiln-relay` serving two more files with the right types.

**Tech Stack:** Preact + TypeScript (web/ui), node:test, esbuild (build.mjs), headless Chrome (web/smoke), Go (cmd/kiln-relay).

**Spec:** Epic #125, sub-project 4 ("the same UI shaped for a small screen"), and `docs/superpowers/specs/2026-10-12-web-ui-design.md`, whose grid has named areas "so part 4 can rearrange them" and whose top bar was to get a `≡`. `glyph.Menu` (`≡`, "the web's sidebar menu") is already in `internal/glyph`.

## For you to check

These change what someone sees or does. Everything after is plumbing.

1. **When the phone layout applies:** the window is under **64ch** wide. That's where the TUI's sidebar (a fifth of the width, at least `chipsWidth`) would leave the scrollback under about 50 characters. A narrow desktop window gets it too, and an iPad held either way doesn't. Your call on the number.
2. **The sidebar becomes a drawer.** A `≡` chip at the left of the top bar opens it over the scrollback, from the left, full height, as wide as the TUI's sidebar at its widest (22ch) or the screen less 4ch. It's a native modal `<dialog>`: focus moves into it, Esc and a tap on the backdrop close it, and the rest of the page is inert while it's open. Tapping a world or character switches and closes it. `+ Connection` opens the picker and closes it.
3. **`≡` carries the unread count.** With the sidebar out of sight, `≡ 3` (and `≡ ● 3` when one is a priority) is the only place you'd see it: the total over every character not showing, in the sidebar's own unread and priority roles. Screen readers hear "Characters, 3 unread".
4. **The picker's list and the filter panel take the scrollback's place**, not the drawer's. The scrollback is only a dimmed backdrop behind the picker anyway, and the filter panel is about the log you'd be looking at. The bottom pane (the filter field, the log bar) stays under them, as on desktop.
5. **Every layer gets a visible way back** on touch, since a phone has no Esc:
   - **The picker, an editor, a log prompt:** a `×` chip at the right of the form's first row.
   - **Log mode:** the `Log` chip in the top bar already closes it.
   - **The password form:** a `Skip` chip, as its "Esc to skip".
   - **The system back gesture** (Android's back, iOS's edge swipe in a browser tab) does the same: opening a layer pushes a history entry, and `popstate` closes the top one. That's the browser's own way of going back, so the page uses it rather than only drawing its own.
6. **Log mode on touch:** the hint row (`/ find · n/N · g date …`) becomes a row of chips: Find, Date, Filter, Tags, Export, Copy, and `↑ ↓` (n/N) once a find has matched. Selecting lines: a tap selects a line, a tap on another extends the selection to it (shift-click's job), and a tap inside the selection clears it. The gutter tap stays as it is. The chips scroll sideways if they don't fit, rather than wrap.
7. **The soft keyboard:**
   - **It comes up only when you tap to type.** On touch, the input doesn't take focus on load or after a switch, and the picker's filter doesn't take focus when it opens (you can tap a row without it). On a keyboard, nothing changes.
   - **The input stays above it.** Android Chrome and Firefox resize the page for the keyboard (`interactive-widget=resizes-content`). Safari doesn't support that ([caniuse](https://caniuse.com/mdn-html_elements_meta_name_viewport_interactive-widget_resizes-content), [WebKit bug 259770](https://bugs.webkit.org/show_bug.cgi?id=259770)), so on iOS the page sizes itself to `visualViewport`.
   - **The return key says Send** (`enterkeyhint="send"`) and sends. A new line has no key on a soft keyboard. You can still paste one. A hardware keyboard keeps Shift+Enter.
   - **History** (↑/↓ from the input's first or last row) has no tap equivalent in this part. MU* players do lean on it, so say if it should: a `↑` chip beside the input, say, or a swipe.
   - **The window size told to the MUCK** stays the size without the keyboard. Otherwise every time the keyboard comes and goes the MUCK gets a resize, and lines wrapped for a 10-row screen.
8. **Tap targets.** On touch, the sidebar's rows, the top bar's and status line's chips, and the editor's buttons grow to 44px tall (Apple's minimum, padding around the one line). The scrollback, log and input stay one line a row, as the TUI's. That's where the reading happens.
9. **Text size stays 16px** (`1rem`). Under 16px, iOS zooms the page when a field takes focus.
10. **The notch and home bar:** the page draws edge to edge (`viewport-fit=cover`), and the top bar and status line pad by the safe-area insets, in their own painted background. The browser's chrome (`theme-color`) takes the status role's background, light and dark.
11. **Installing (PWA):**
    - **A manifest:** name "Kiln", `display: standalone`, its scope and start at `/kiln/`, its colors from the built-in theme. Its name and description are strings in the catalog, filled in by `build.mjs` as `index.html`'s are.
    - **Icons are yours to make.** It needs a square icon at 192 and 512px (one maskable, so Android can crop it to a circle), and a 180px `apple-touch-icon`. Until they exist the plan uses a placeholder (`≡` isn't it: maybe a kiln?). The favicon is `data:,` today and could come from the same art.
    - **No install button.** iOS has no way for a page to offer one (no `beforeinstallprompt`). Android Chrome shows its own when it decides to. Docs say how on each.
12. **The service worker caches nothing, in this part.** It's there for notifications, and because Chrome's own install prompt wants a fetch handler ([Chrome](https://developer.chrome.com/blog/update-install-criteria)). It hands every request to the network unchanged. Caching the page and the 6 MB wasm would make a phone start faster, but a page and wasm from different releases would break in ways that are hard to see. That's a part of its own, with versioned file names. The relay's `no-cache` already makes a reload a cheap 304.
13. **Notifications go through the service worker.** Android Chrome refuses `new Notification()` from a page ([Chrome](https://developer.chrome.com/blog/notifying-you-of-changes-to-notifications)), and an iPhone shows notifications only from a Home Screen app (iOS 16.4 and later; `notify_unsupported` already says so). So the page shows them with `registration.showNotification`. A tap brings Kiln forward and switches to the character, as a click does now. This fixes Android Chrome, which today logs "Chrome on Android only shows them from a service worker" and shows nothing.
14. **What a phone still can't do, and won't in this part:**
    - **Kiln stays connected only while it's on screen.** iOS suspends a backgrounded page and its WebSocket, installed or not. That's part 5, the detachable relay. A notification arrives only while Kiln is open, on screen or just left.
    - **An installed iPhone app has its own storage**, apart from Safari's ([WebKit bug 181849](https://bugs.webkit.org/show_bug.cgi?id=181849)). Worlds set up in Safari don't follow it to the Home Screen. `/backup` in one and `/restore` in the other moves them, and the preset seeds both. On the upside, a Home Screen app isn't subject to Safari's 7-day storage cap ([WebKit bug 237350](https://bugs.webkit.org/show_bug.cgi?id=237350)), which matters for a client that keeps logs. The docs say both.

## Global Constraints

- **Strings come from the catalog,** with a `Strings:` trailer on each commit that adds one. Tests read the catalog.
- **Colors come from theme roles.** The drawer, its backdrop and the chips use existing roles (`sidebar`, `sidebar.unread`, `sidebar.priority`, `form.button`, the dim roles for the backdrop). A new role only if one's missing, added to `roles.go`, `Roles`, `default.toml` and `docs/themes.md`.
- **The TUI's goldens never move.** This plan doesn't touch `internal/ui`.
- **The desktop web goldens never move.** Every change is behind `narrow` or `touch`. The phone gets goldens of its own.
- **The browser's way first:** `<dialog>` for the drawer, history for back, `enterkeyhint` for the return key, CSS env() for the insets.
- **Pre-1.0, no personal names.** Kit, Rook, Ash and `fm` in tests and docs.

## Review Focus

1. **A keyboard user in a narrow desktop window** gets the drawer but keeps every key: Ctrl+↑/↓ and Alt+↓/↑ still switch with the drawer shut, and focus still goes to the input on load. → Task 1's and Task 5's tests (narrow without touch).
2. **History and layers stay in step.** Back closes exactly one layer, and a layer closed another way (Esc, ×, a save) doesn't leave a stray entry that makes the next back do nothing. → Task 4's tests.
3. **The drawer and the picker never fight.** `+ Connection` in the drawer closes it before the picker opens, and `/open` with the drawer open does the same. → Task 2's tests.
4. **iOS's visual viewport:** the bottom pane sits on the keyboard with the scrollback scrolled to the end, and nothing jumps when the keyboard goes. → hand check, Task 5.
5. **No version skew from the service worker:** it never answers from a cache, and a new release reaches an installed app on its next start. → Task 7's smoke step.
